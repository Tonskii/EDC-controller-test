=====================================================================
 ZKTeco C3-400 Plus — full test cycle through Swagger
 Controller SN: AJU8261200103      Swagger: http://<pc-ip>:8088/swagger
=====================================================================

HOW TO USE
- In Swagger: open the endpoint → "Try it out" → paste the JSON into the request body
  (or fill the listed parameters) → Execute.
- Every command answer contains "commandId". Check it with STEP 0.2 before moving on.
  Wanted result: "status": "Succeeded", "returnCode": 0  (queries return the number of rows).
- "sn" may be left empty ("") while only one controller is connected.
- Test data used everywhere:  PIN 1001 · card 0x1d0456 (the test card swiped on 2026-10-20)
  · time rule (timezone) 2 · doors 1-4 · DevID 190 (controller AJU8261200103).
- Add ?preview=true to any POST/PUT/DELETE to see the command without sending it.

Expected wire text is shown under each step ([TAB] = tab character). If a step fails,
copy the console block of that command (yellow "sending" + green/red "result").


---------------------------------------------------------------------
 STEP 0 — PREPARATION
---------------------------------------------------------------------

0.1  Is the controller connected and polling?
     GET /api/devices
     → "heartbeats" must keep increasing when you execute it again after a few seconds.
     → "capabilitiesSource" should be "registration" or "saved registry file" (not "unknown").

0.2  How to check any command (use after every step)
     GET /api/commands/{id}
       id          = commandId from the answer
       waitSeconds = 15
     → status Succeeded / Failed, returnCode, meaning, and "queryData" for queries.

0.3  Fix the controller clock (it was 6 h ahead — time rules depend on it)
     POST /api/device/sync-time
       sn = AJU8261200103
     Expected:  C:<id>:SET OPTIONS DateTime=<seconds>
     Check:     POST /api/device/options/get   with body
{
  "sn": "AJU8261200103",
  "names": ["DateTime"]
}
     → GET /api/commands/{id} → queryData shows the controller time.


0.4  IMPORTANT — is multi-card mode SWITCHED ON?
     The controller registers with AccSupportFunList[7]=1, which only means "multi-card is
     SUPPORTED". Cards in table mulcarduser are only used when MulCardUserFunOn=1 is ACTIVE.
     If it is 0, every swipe gives EVENT 27 even though the card is in mulcarduser.

     Read it:   POST /api/device/options/get
{
  "sn": "AJU8261200103",
  "names": ["MulCardUserFunOn"]
}
     → console prints "Option MulCardUserFunOn = 0/1" (also in GET /api/commands/{id} → queryData)

     Switch it on:   POST /api/device/options/set
{
  "sn": "AJU8261200103",
  "options": { "MulCardUserFunOn": "1" }
}
     Expected:  C:<id>:SET OPTIONS MulCardUserFunOn=1
     Then read it again (above). Reboot the controller if it still says 0.

     Alternative if it will not switch on: keep cards in the user table instead — in STEP 3 add
     "target": "UserTable"  → DATA UPDATE user CardNo=1901654[TAB]Pin=1001

0.5  Clean up broken test users (only once)
     The user query showed two rows created earlier with SPACES instead of tabs, e.g.
       pin=1 Password=234 Group=0 StartTime=0 EndTime=0 Name=Janez Privilege=0 DevId=190
     The whole text became the PIN. Fields MUST be separated by TAB — in POST /api/raw write [TAB].
     Easiest clean-up (removes all users, cards and access on the controller):
     DELETE /api/users/all      confirm = true, sn = AJU8261200103

 STEP 1 — CREATE THE TIME RULE ("timezone" 2)
---------------------------------------------------------------------
     Mon–Fri 07:00–12:00 and 12:30–17:00, Sat+Sun 08:00–12:00, holidays none.

     PUT /api/timerules
{
  "sn": "AJU8261200103",
  "timezoneId": 2,
  "weekdays": ["07:00-12:00", "12:30-17:00"],
  "weekend": ["08:00-12:00"]
}
     Expected:
     DATA UPDATE timezone TimezoneId=2[TAB]SunTime1=52430000[TAB]SunTime2=0[TAB]SunTime3=0
       [TAB]MonTime1=45876400[TAB]MonTime2=80610980[TAB]MonTime3=0 ... (Tue–Fri same as Mon)
       ... [TAB]SatTime1=52430000 ... [TAB]Hol3Time3=0
     (07:00-12:00 = 700<<16 + 1200 = 45876400; decode any value with GET /api/timerules/decode/{value})

     Tip for testing at the door right now: use a range that includes the current time, e.g.
{
  "sn": "AJU8261200103",
  "timezoneId": 2,
  "everyDay": ["00:00-23:59"]
}

---------------------------------------------------------------------
 STEP 3 — ADD THE CARD
---------------------------------------------------------------------
     IMPORTANT: use the number the CONTROLLER reads, not the number printed on the card.
     Swipe the card once before adding it. The console shows e.g.
        EVENT 27 "Card/user not registered" door=4 IN card=1d0456
     That "card=" value is HEX. Enter it with a 0x prefix (or as decimal 1901654):

     POST /api/cards
{
  "sn": "AJU8261200103",
  "pin": "1001",
  "cardNo": "0x1d0456",
  "cardType": 0,
  "lossCardFlag": 0
}
     Expected:
     DATA UPDATE mulcarduser Pin=1001[TAB]CardNo=1d0456[TAB]LossCardFlag=0[TAB]CardType=0

     Why the printed number does not work: 0x1d0456 = 1901654 decimal = Wiegand-26 facility 29,
     card 1110 — a card may be printed as "1901654", "029,01110" or "0001901654". Typing the
     printed digits as decimal produces a different hex value and the controller answers EVENT 27.
     Check what was stored with STEP 6.2: the stored cardno must equal the event's card= value.


---------------------------------------------------------------------
 STEP 4 — GIVE ACCESS (doors 1–4 during time rule 2) — WITH DevID
---------------------------------------------------------------------
     The C3-400 Plus reports AccSupportFunList[26]=1 = "tables have a DevID field", so the
     userauthorize row needs DevID. Every controller has its OWN DevID — for AJU8261200103 it is 190.

     Store it once per controller (saved in ./devices, survives restarts):
     PUT /api/devices/{sn}/devid        sn = AJU8261200103, value = 190
     (or in appsettings.json:  "Push": { "DevIds": { "AJU8261200103": 190 } } )
     After that the access calls need no devId. Sending "devId" in a request overrides it.

     PUT /api/access
{
  "sn": "AJU8261200103",
  "pin": "1001",
  "doors": [1, 2, 3, 4],
  "timezoneId": 2,
  "includeDevId": "Yes"
}
     Expected:
     DATA UPDATE userauthorize Pin=1001[TAB]AuthorizeTimezoneId=2[TAB]AuthorizeDoorId=15[TAB]DevID=190
     If no DevID is stored for the controller the API answers 400 with instructions instead of guessing.
     The answer's "notes" says why DevID was / was not sent.

     How includeDevId works:
       "Yes"  → always adds DevID (value: request devId → stored per controller → appsettings)
       "Auto" → adds DevID only if the controller reported bit 26 when it registered. The server now
                saves that in ./devices/AJU8261200103.registry.txt, so it also works after a server
                restart. If the controller is unknown, the note says "DevID: NOT sent".
       "No"   → never adds it
       Giving "devId" alone also forces it to be sent.

     Other door combinations (always with DevID):
       only doors 1+2:  "doors": [1, 2]    → AuthorizeDoorId=3
       only door 3:     "doors": [3]       → AuthorizeDoorId=4
       24/7 rule:       "timezoneId": 1

     Several users at once — PUT /api/access/batch
{
  "sn": "AJU8261200103",
  "items": [
    { "pin": "1001", "doors": [1, 2], "timezoneId": 2, "includeDevId": "Yes" },
    { "pin": "1002", "doors": [3, 4], "timezoneId": 2, "includeDevId": "Yes" }
  ]
}
     Expected (one command, records separated by LF):
     DATA UPDATE userauthorize Pin=1001[TAB]AuthorizeTimezoneId=2[TAB]AuthorizeDoorId=3[TAB]DevID=190
       [LF]Pin=1002[TAB]AuthorizeTimezoneId=2[TAB]AuthorizeDoorId=12[TAB]DevID=190
     (PIN 1002 must exist as a user first — add it like step 2.)

     Which tables use DevID: per the protocol only the door/device tables (userauthorize, first-card and
     multi-card opening, DoorParameters, ReaderParameters, …). user, mulcarduser, timezone and holiday
     have NO DevID field — steps 1–3 stay exactly as they are.


---------------------------------------------------------------------
 STEP 5 — TEST AT THE DOOR (optional but the real proof)
---------------------------------------------------------------------
     Swipe the test card (0x1d0456) at a reader of door 1–4. Console (magenta):
       EVENT 0  "Normal open after verification" door=1 IN pin=1001 card=...   → OK
       EVENT 22 "Illegal time zone"         → outside time rule 2 (check clock / rule)
       EVENT 23 "Access denied"             → no access for this door (step 4)
       EVENT 27 "Card/user not registered"  → card not found: MulCardUserFunOn (step 0.4), card number
                                             (compare event card= with step 6.2) or user missing
       EVENT 29 "Card/user validity expired"→ validFrom/validUntil or clock (step 0.3)

 STEP 6 — QUERY: CHECK THAT EVERYTHING EXISTS ON THE CONTROLLER
---------------------------------------------------------------------
     Each query returns a commandId → GET /api/commands/{id}?waitSeconds=15 → "queryData".

6.1  Users          POST /api/users/query        sn = AJU8261200103
     Expected:  DATA QUERY tablename=user,fielddesc=*,filter=*
     Look for:  user uid=.. cardno= pin=1001 password=1234 group=0 starttime=861408000 endtime=996364799 name=Test User ...

6.2  Cards          POST /api/cards/query        sn = AJU8261200103
     Expected:  DATA QUERY tablename=mulcarduser,fielddesc=*,filter=*
     Look for:  pin=1001 ... cardno=1d0456   (must equal the card= of the swipe event)

6.3  Access         POST /api/access/query       sn = AJU8261200103
     Expected:  DATA QUERY tablename=userauthorize,fielddesc=*,filter=*
     Look for:  pin=1001 authorizetimezoneid=2 authorizedoorid=15 devid=190

6.4  Time rules     POST /api/timerules/query    sn = AJU8261200103
     Expected:  DATA QUERY tablename=timezone,fielddesc=*,filter=*
     Look for:  timezoneid=2 ... montime1=45876400 ...

6.5  Counts (quick check)
     POST /api/users/count                        → DATA COUNT user
     POST /api/tables/{table}/count   table = mulcarduser | userauthorize | timezone

6.6  Only PIN 1001 (filter syntax differs per firmware — try, not required)
     POST /api/tables/{table}/query
       table     = user
       fieldDesc = *
       filter    = Pin=1001
     Expected:  DATA QUERY tablename=user,fielddesc=*,filter=Pin=1001

6.7  Stored door events (swipes from step 5)
     POST /api/transactions/query   newOnly = false
     Expected:  DATA QUERY tablename=transaction,fielddesc=*,filter=*


---------------------------------------------------------------------
 STEP 7 — DELETE EVERYTHING (order: access → card → user → time rule)
---------------------------------------------------------------------
7.1  Access         DELETE /api/access/{pin}         pin = 1001, sn = AJU8261200103
     Expected:  DATA DELETE userauthorize Pin=1001
     (Pin is the delete condition and removes the row for every DevID. If the controller answers
      an error, send it with DevID through POST /api/raw:
{
  "sn": "AJU8261200103",
  "command": "DATA DELETE userauthorize Pin=1001[TAB]DevID=190",
  "label": "Delete access 1001 with DevID"
}
     )

7.2  Card           DELETE /api/cards/{pin}          pin = 1001, cardNo = 0x1d0456, sn = AJU8261200103
     Expected:  DATA DELETE mulcarduser Pin=1001[TAB]CardNo=1d0456
     (leave cardNo empty to delete ALL cards of the user: DATA DELETE mulcarduser Pin=1001)

7.3  User           DELETE /api/users/{pin}          pin = 1001, sn = AJU8261200103
     Expected:  DATA DELETE user Pin=1001

7.4  Time rule      DELETE /api/timerules/{timezoneId}   timezoneId = 2, sn = AJU8261200103
     Expected:  DATA DELETE timezone TimezoneId=2

     Shortcut for 7.1–7.3 in one call (three commands, same order):
     DELETE /api/users/{pin}/complete    pin = 1001, sn = AJU8261200103

 IF SOMETHING FAILS
---------------------------------------------------------------------
     GET /api/commands?sn=AJU8261200103          all commands with status + returnCode
     GET /api/devices/AJU8261200103/traffic      last requests/responses (raw)
     DELETE /api/devices/AJU8261200103/queue     cancel commands still waiting

     Common return codes:
       -11  incorrect data parameter          -620  data format incorrect
       -621 table does not support a field    -629  incorrect table name
       -13  command does not exist            -708  firmware does not support this command
     Send the file logs/push-traffic-<date>.log together with the failing commandId.
